# Radial Dial Performance Results — 2026-09-12

## Environment

- CPU: Intel Core i5-10210U (4 cores / 8 threads)
- Display: 1920×1080
- Quickshell configuration: end4-pC
- Radial source baseline: owner commit `e2f27a8`
- Low-end profile: enabled by automatic integrated-GPU detection

The harness samples the Quickshell main process CPU from `/proc`, checks its
resident memory, and
measures layer open/close latency. Each active workload repeatedly opens the
dial, holds it static or moves the pointer, and closes it again. The drag
workload holds the pointer within one slice, so it cannot reorder the user's
configuration. Active runs anchor the dial at the center of the current monitor
and restore the original pointer position afterward, avoiding edge-clamping
distortion.

## Result

No runtime change was retained. The owner baseline already unloads the panel,
Canvas, timers, and animations while closed, and every isolated candidate was
within noise or worse in a matched end-to-end workload.

| Comparison | Baseline | Candidate | Verdict |
|---|---:|---:|---|
| Closed CPU median, radial loaded vs disabled | 39.808% | 39.791% | No measurable idle cost |
| Closed CPU mean, radial loaded vs disabled | 42.760% | 42.404% | 0.8% difference; noise |
| Threaded Canvas, idle-motion CPU median | 48.759% | 51.212% | Discard: 5.0% worse |
| Threaded Canvas, motion CPU median under synthetic CPU load | 41.466% | 43.935% | Discard: 6.0% worse |
| Single initialization, idle-motion CPU median | 48.759% | 45.744% | Discard: below 10% threshold and not repeatable under load |
| Python opener vs native Lua candidate, CPU median | 42.602% | 42.211% | Discard: 0.9% difference |
| Python opener vs native Lua candidate, open median | 327.906 ms | 327.399 ms | Discard: 0.2% difference |
| Drag repaint removal, centered high-rate per-run CPU median | 57.442% | 53.933% | Discard: 6.1% improvement, below threshold |

The native Lua context helper was faster in isolation (about 18 ms median
versus 154 ms for the Python helper), but an immediate end-to-end control run
suggested that panel creation dominates perceived opening latency. Keeping the
micro-optimization would therefore add maintenance cost without improving the
menu.

## Reproduce

Run the same workload against the active end4-pC shell:

```bash
python3 benchmarks/radial_benchmark.py \
  --mode motion --duration 3 --repetitions 7 \
  --output /tmp/radial-motion.json
```

Available modes are `closed`, `static`, `motion`, and `drag`. Add
`--load-workers 2` to exercise the dial under controlled CPU contention.

The table above records exploratory sequential runs made while testing temporary
candidate patches. Those discarded patches are not part of the final branch,
so the exact historical comparisons are not reproduced by a single command.
The values are descriptive rather than statistical estimates of causality:
experiments used five to seven repetitions, and some early files predated the
per-repetition aggregate added to the final harness.

CPU percentages in the table cover the Quickshell main process only. Short-lived
helper and compositor CPU, transient memory, memory-pressure behavior, GPU load,
and whole-desktop responsiveness were not measured. RSS was sampled after each
run, while the menu was closed, so it is useful only as a leak smoke check.

## Interpretation

These measurements found no detectable closed-state Quickshell-main-process CPU
cost from the radial scope on this machine. Source inspection explains that
result: opening creates a new layer and QML content, while closing deactivates
the Loader, destroying the panel, Canvas, timers, and animations. The tests do
not establish the cause of slowdown under RAM pressure or account for GPU and
compositor work.
